## 一、为什么做这个实验

手上一直缺一份能拿出来的东西。Service 和 Ingress 做蓝绿、做灰度，这两套东西我讲过很多遍，
但每次讲完总有人问同一个问题：到底该用哪个。

以前我的回答基本是"看场景"，说完自己都觉得虚。这次索性在一台空机器上把两边都跑一遍，
把现象摆出来，看能不能给一个我自己信得过的判断。

目标机是 192.168.100.128，Rocky Linux 10.0，4 核 3.5G。机器是干净的，docker、podman、
k3s 什么都没装，80 和 443 也空着。这种环境我最喜欢，不用先花时间清理别人的遗留。

---

## 二、第一个坑：docker.io 直接不通

装之前我先做了一轮勘测。这一步算习惯——踩过的坑太多，宁可多花十分钟。

结果出来的时候有点意外：

```
index.docker.io       -> 000
registry-1.docker.io  -> 000
quay.io               -> 401
ghcr.io               -> 401
```

三个 docker.io 的域名全是 000。我第一反应是"这台机器的出口被限了"，
但 quay 和 ghcr 都是 401（能握手），说明整体出口没被封，是单独把 docker.io 挑出来了。

这事儿的麻烦在于，我准备的演示镜像 `hashicorp/http-echo` 就在 docker.io 上。
所以镜像加速这一步跳不过去，配不上就干不下去。

## 三、第二个坑：registry.k8s.io 看着通，其实不通

这个是这次最值得记的一个。

我做完 docker.io 的加速配置，顺手测了下 registry.k8s.io：

```
registry.k8s.io -> 401
```

401 意味着网络是通的（只是没认证）。我心里就把它划到"没问题"那一栏了，
只在 `registries.yaml` 里给 docker.io 配了加速，registry.k8s.io 放着没管。

然后装 K3s，节点起来了，一切正常。我心里更踏实了。

接着装 ingress-nginx，控制器 Pod 一直起不来。`describe` 出来是 `ImagePullBackOff`。

我盯着那个 401 看了半天，实在想不通哪里不对，就换了个角度，直接去拉一次真实的 manifest：

```bash
curl -sv --max-time 10 https://registry.k8s.io/v2/
```

```
* Connected to registry.k8s.io port 443
* SSL connection using TLSv1.3
< HTTP/2 401
```

还是 401。TLS 也正常。看着一点毛病都没有。

后来我才想到，`/v2/` 这个端点只回答一个问题——自己是不是一个 registry。
至于手里有没有那个镜像，它不管。

再往下走一步就露馅了：请求具体镜像的 manifest 时，registry.k8s.io 返回 **307 重定向**，
把我导到 `*.pkg.dev`（Google 的 Artifact Registry），而那个域名在这台机器上是 refusal。

也就是说，registry.k8s.io 在我这儿只是个指路牌，指的方向过不去。

补上加速端点、重启 K3s，卡住的 Job 和 Pod 删掉重新 apply，控制器 27 秒就起来了。

那次之后我给自己记了一条：测仓库通不通，只打 `/v2/` 会得到假的安心。
得真去拉一个 manifest，才能看到重定向这一层。我以后不会再拿 401 当通过了。

## 四、SELinux 那件事

这台机器 SELinux 是 Enforcing。

按老经验，跑容器碰到 Enforcing 是要出事的，我本来打算先 `setenforce 0` 再说。
后来想了一下，K3s 的安装脚本这些年一直在处理这件事，就先照原样装了。

结果节点直接 Ready，什么异常都没有。回头看，安装脚本自己去 Rancher 源上装了
`k3s-selinux` 策略包并加载了。K3s 自己带了策略，我没必要去动系统安全开关。

幸好没先关。Enforcing 关掉容易，再打开要全盘 relabel，代价不小。

## 五、入口那一步也想歪了一次

ingress-nginx 的 baremetal 清单，Service 默认给的是 NodePort。

装完我做了一次裸测：

```bash
curl -s -o /dev/null -w 'HTTP %{http_code}\n' http://127.0.0.1/
```

```
HTTP 404
```

看到 404 我第一反应是"坏了"。

其实那个 404 是 ingress-nginx 的默认后端返回的——控制器活着，只是还没有任何 Ingress 规则匹配。
真正坏掉的样子是 `curl: (7) Failed to connect`。

我后来把清单里的 Service 改成了 LoadBalancer，K3s 自带的 servicelb 起了一个 DaemonSet，
用 hostPort 把 80 和 443 直接绑到宿主。这样访问不用带端口号，跟真实入口更接近。

顺带也验证了另一件事：数字本身不等于结论，404 有时候是健康信号。

## 六、实验本身：两组现象

### Service 层

蓝绿很简单，改 `web-bg` 这个 Service 的 selector，从 `version=blue` 改成 `version=green`。
一发下去，Endpoints 列表整个换了一批 IP，后面的请求 100% 走新版本。

我特意在切换前后各打了 50 次，中间没有任何一次落在旧版本上。这就是蓝绿的样子：
**一瞬间全换，没有过渡**。快，干净，代价是没有观察期。

灰度我一开始想的是给 Pod 打中间态标签，写了半天脚本，越写越别扭。后来停下来想了想：
Service 的转发是四层的、随机、无状态，标签怎么打，最后都归结成一件事——后端 Pod 的数量比。
那我直接用副本数表达比例就行了。

于是就有了那张表：5:5 实测 47:53，9:1 实测 87:13，7:3 实测 75:25，1:9 实测 8:92。

看数据的时候有个细节让我停顿了一下：9:1 应该是 10%，实测 13%。我又跑了几轮，
在 47% 和 53% 之间来回晃。这就是 kube-proxy 随机转发的统计涨落，不是配错了。

这件事对做发布的实际意义比比例本身更大：**小流量下"今天 20% 明天 35%"是常态**，
指望它稳定在某个精确值上不太现实。

### Ingress 层

Ingress 的权重灰度让我第一次觉得"这才是灰度该有的样子"。

`canary-weight` 改一个数字就能调比例，20 就是 20，后端几个 Pod 都不影响。
实测 20→20%、50→46%、80→75%、100→100%，波动比 Service 层小得多。

请求头那个场景我本来没抱期望，跑出来才发现它的价值：
不带 `X-Canary` 头的请求 100% 走旧版本，带 `X-Canary: always` 的 100% 走新版本。
而且我特意试了一个 `X-Canary: other`——值不匹配的时候它不会掉进权重规则里随机分配，
而是干净地回落到主入口。

这一下就清楚了：它干的活儿是路由，跟比例完全是两回事。
真机联调、测试账号先行，用这个一点都不会影响真实用户。Service 层完全做不到这件事。

## 七、回看

一开始那个"到底该用哪个"的问题，跑完我给出的答案是分层的。

蓝绿在两层都行。Service 改 selector 和 Ingress 改后端名，语义是一样的原子切换，
差别只在切换点落在哪一层。

灰度就得往上移到 Ingress。Service 层的天花板摸得很清楚：比例分辨率受 Pod 总数限制，
做不了 1%，更做不了定向。它在能力模型里压根没有"请求"这个层级，补精度补不出来。

不过我也给自己留了个提醒：`canary-*` 这套注解是 ingress-nginx 私有的，不是 K8s 标准。
换个控制器就得换成 CRD 或者别的注解。所以对外讲的时候，得说清这是"入口层灰度"这个能力，
而不是"K8s 有 canary-weight 这个字段"。
